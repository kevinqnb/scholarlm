## Session 2026-09-22

### Prompts

- Create `analysis/match_cache.py` and a job script `analysis/match_cache.sh`. Its
  only purpose: take a list of experiment ids and per-dataset matching-configuration
  dicts, compute and cache matches. Start with
  `2026-09-21-pond-extraction-gemma27b-full-01`; pond matching config strict on
  `document_id`, `attribute`, `point_value`, `unit`, fuzzy on `name`, `ecosystem`.
- Threshold 1/3 for pond; use `match_datasets` from `src/scholarlm/utils/data.py`;
  bring `cached_match` from `analysis/loaders.py` directly into this script so it
  becomes the centralized point where all matching code and running happens.
- "It's smart to always cache with a threshold of 0, since recomputing a matching
  with a larger threshold can already reuse whatever is cached, and just filter it
  further. Is there a smart way we can always store the full 0.0-threshold cache,
  with the selected fuzzy threshold applied on top and adaptable?"
- "So if I wanted to use a cached match in another script, with some chosen
  threshold, how would I do that?"

### Implemented

`analysis/match_cache.py` is now the centralized place matching configuration and
matching runs live: `MATCHING_CONFIGS["pond"]` (strict on `document_id`,
`attribute`, `point_value`, `units`; fuzzy on `name`, `ecosystem`; threshold 1/3),
`cached_match`/`edges_above_threshold`/`load_match_cache` wrapping
`scholarlm.utils.data.match_datasets`, and `build_match_cache(experiment_id)` which
resolves the run via `experiments/utils.py`, loads `final.json` + ground truth, and
writes `match_cache.pkl` into that run's own results directory. The cache is always
built at `fuzzy_threshold=0.0` and a threshold is applied on top via
`edges_above_threshold` — matching the convention `analysis/metrics.py` and every
`calibration*.py`/`probe_pca.py` caller of `cached_match` already use, so any
threshold can be applied later without redoing the O(n_gt × n_extraction) scan. Along
the way, fixed a real dtype mismatch between ground truth's numeric `point_value` and
the extraction pipeline's raw string `point_value` output, and added scientific-
notation parsing (`_parse_numeric`) for the small fraction of extraction rows whose
`point_value` isn't a plain float. `analysis/match_cache.sh` is a gitignored SGE job
wrapper, following `analysis/run_calibration_full.sh`'s convention.

A tiny hand-built fixture test passed (twice — once before, once after the
threshold-caching redesign). The one real full-scale run
(`2026-09-21-pond-extraction-gemma27b-full-01`, pre-redesign cache semantics)
succeeded directly in the shell: 3333 ground-truth rows, 11022 extraction rows, 2312
candidate edges at threshold ≥ 1/3, 1094 matched pairs, 22m26s. A second full-scale
run to confirm the post-redesign cache reproduces equivalent numbers was killed
(SIGKILL, exit 137) after ~18 minutes on the interactive shell — likely the SCC login
node's CPU-time cap, not a code issue. That confirmation is outstanding and needs a
real `qsub` submission of `match_cache.sh` rather than another interactive-shell run.
